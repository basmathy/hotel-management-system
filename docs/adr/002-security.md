# ADR 002: пользовательские JWT и отдельный INTERNAL-контур

Принято: 2026-11-07.

Booking выдаёт HS256 JWT на 3600 секунд. Gateway, Hotel и Booking самостоятельно
проверяют подпись, срок, issuer=hotel-platform, audience=hotel-api и числовой sub.
Учитываются только роли USER и ADMIN. Пользовательская регистрация всегда создаёт
USER; поле role в регистрационном JSON не назначает права. Пароли хешируются BCrypt.
DTO ответов не содержат хеша.

Административные операции защищены @PreAuthorize. Политика BookingAccessPolicy
разрешает владельцу доступ к своей брони, ADMIN — к любой. Пользователь не может
назначить себе роль через публичный API.

Hotel INTERNAL API требует отдельный X-Internal-Token с постоянным по времени
сравнением. Роль ADMIN в JWT этого доступа не даёт. Gateway запрещает /internal/**
и удаляет X-Internal-Token перед маршрутизацией. Сервисный токен не передаётся
клиенту и не является JWT-ролью. Correlation ID ограничен безопасными символами
и длиной 64, иначе генерируется UUID. MDC очищается в finally.

JWT_SECRET (минимум 32 байта) и INTERNAL_TOKEN (минимум 12 символов) задаются
окружением. Локальные демонстрационные значения разрешены только профилем demo.
Секреты и пароли не логируются. HTTPS и изоляция INTERNAL API на уровне сети
требуются при размещении за пределами локальной машины; сервис registry не
предназначен для публикации в интернет.

Цена простоты: симметричный ключ есть у проверяющих сервисов; для независимых
доверительных границ следует перейти на асимметричную подпись/JWKS. Смена роли
и удаление пользователя не отзывают уже выданный JWT мгновенно: срок до часа
(стандартная проверка допускает clock skew до 60 секунд). Refresh/revocation
в эту версию не входят.
