# ADR 003: локальные транзакции, сага и журнал компенсаций

Принято: 2026-11-07.

Распределённая транзакция БД/HTTP не используется. BookingTransactionService
сначала фиксирует PENDING с UUID и уникальным (owner_id, request_id).
Входные hotelId, requestedRoomId и даты неизменяемы. Повтор ключа с теми же
параметрами возвращает имеющуюся запись; с другими — 409. PENDING может быть
возвращён параллельному повтору с 202; клиент читает GET /api/bookings/{id}.
Одна и та же операция не запускает вторую сагу.

BookingSagaCoordinator вызывает Hotel между локальными транзакциями.
operationId = bookingId + "-" + selectedRoomId. Номер выбирается и сохраняется
под блокировкой Booking перед reserve. Автоподбор при однозначном 409 пробует
следующего кандидата с отдельным operationId. Транспортная ошибка не означает
отказ выделения: бронь отменяется и запускается компенсация.

В финальной транзакции PENDING становится CONFIRMED. Recovery отменяет только
всё ещё PENDING старше saga.recovery-age. Подтверждение и recovery блокируют
одну строку; после CANCELLED позднее подтверждение не меняет статус.
HTTP не выполняется под локальными блокировками Booking.

При пользовательской отмене, ошибке или recovery CANCELLED и CompensationTask
фиксируются атомарно. Если при автоподборе номер ещё не выбран, HTTP-операции
не было и задача не нужна. Компенсация вызывает release вне транзакции,
затем отдельно сохраняет успех или следующую попытку. Сбой после успешного
release до сохранения результата безопасен: повторный release идемпотентен.

CompensationRetryScheduler читает до 100 готовых задач, использует ограниченную
экспоненциальную отсрочку (2..256 секунд), не удаляет завершённые задачи.
Несколько экземпляров могут одновременно доставлять release; Hotel гарантирует
однократный эффект. PendingBookingRecoveryScheduler обрабатывает до 100
зависших PENDING за проход; он не отменяет уже CONFIRMED.

Тайм-аут HTTP задаётся на уровне JDK HttpClient (connect 0.5 с, response 1 с).
Retry: до 3 попыток с паузой 100 мс только при транспортной ошибке/5xx.
4xx не повторяются. Reserve/release дополнительно проверяют operationId и статус
в подтверждении Hotel: пустой или несогласованный ответ не считается успехом.
Release для уже удалённого номера (404) считается завершённым: запрет удаления
номера с историей гарантирует отсутствие удерживаемого слота. Circuit breaker: окно 10, минимум 4 вызова, 50% ошибок,
открытие на 10 с. Значения изменяются конфигурацией, а recovery по умолчанию
через 2 минуты оставляет запас на обычный HTTP-бюджет.

Отметки RELEASED и ключи идемпотентности хранятся без автоматической очистки.
При будущем введении TTL нужно согласовать горизонт всех повторов: простое
удаление tombstone вновь разрешит запоздалое выделение. Нужны мониторинг
незавершённых задач и постоянная БД для переживания перезапуска процесса.
