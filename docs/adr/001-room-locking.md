# ADR 001: сериализация операций по строке номера

Принято: 2026-11-07.

В каждый момент для одного номера допустим только один HELD-интервал,
пересекающий заданные даты. Проверка отсутствия пересечений сама по себе
не защищает от двух конкурентных вставок.

Reserve и release сначала получают PESSIMISTIC_WRITE на Room с ограничением
ожидания 2000 мс. Затем читают ключ операции, проверяют идентичность,
состояние, эксплуатационную доступность и пересечения. Запись резервирования
и изменение timesBooked выполняются в той же транзакции. UPDATE/DELETE номера
используют ту же блокировку. Создание номера и удаление отеля сериализованы
по строке Hotel. Сервисы не используют JVM-lock для защиты данных.

Интервалы полуоткрытые: existing.checkIn < requested.checkOut AND
existing.checkOut > requested.checkIn. Соседние интервалы разрешены.

RELEASED-записи не удаляются: они блокируют поздний reserve того же operationId.
Первый release для неизвестной операции создаёт RELEASED без уменьшения счётчика.
Уникальность operationId закреплена PK, (hotel_id, number) — unique constraint.
timesBooked — число HELD-записей всех дат, включая завершившиеся проживания;
это счётчик неотменённых выделений, а не только текущая физическая загрузка.

Для идемпотентного создания Booking блокируется строка пользователя и проверяется
unique(owner_id, request_id). Параллельные запросы разных пользователей не
сериализованы друг с другом. Подтверждение, выбор номера, отмена и recovery
сериализованы по строке Booking; @Version даёт дополнительную защиту.

Следствия: защита работает между экземплярами с общей БД; операции одного
пользователя или номера сериализованы. При тайм-ауте/конфликте API возвращает 409.
JPA hint поддерживается не всеми СУБД одинаково; для H2 дополнительно установлен
LOCK_TIMEOUT. Перед сменой СУБД следует проверить реальный диалект и тайм-ауты.
H2 in-memory одного JVM не разделяется между процессами.
